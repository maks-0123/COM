# Контракт ingest для сценария B: позиционирование по LTE

Статус: черновик для обсуждения, ноябрь 2026. Дополняет `docs/handoff-context.md`
(раздел 7, сценарий B). Документ описывает, что такое сервис ingest при
позиционировании по LTE: какие измерения он принимает, как из них получает
позицию и как пишет результат в `ScenarioFile`.

## 1. Поток данных

```
UE (модем на тележке) → eNodeB → измерения (RSSI/TA) → ingest → движок позиционирования
                                                              ↓
Magma (Orc8r/AGW): события, IMSI ↔ SIM, конфиги → реестр тележек и станций
                                                              ↓
                              последний срез per cart → ScenarioFile (атомарно)
                                                              ↓
                                              карта читает снимок раз в секунду
```

Ключевое разделение ролей:

- **Magma отвечает за связь и идентичность**: attach, сессия, IMSI абонента.
  Она **не поставляет измерения сигнала** — в её API (NMS/Orc8r) PHY-измерения
  не выставлены. Это принципиально: источником измерений является eNodeB,
  а не Magma.
- **Ingest отвечает за геометрию**: принимает измерения, считает позицию,
  решает, что попадёт в снимок.
- **Карта не меняется**: она рисует `ScenarioFile` и его `method`-дискриминатор
  уже умеет все три метода сценария B (`rssi-multilateration`, `ecid-ta`, `cell-id`).

## 2. Источник измерений (решение нужно)

LTE-измерения (RSRP по соседям, Timing Advance) живут в eNodeB, не в Magma.
Варианты получения:

| Вариант | Когда подходит | Комментарий |
|---|---|---|
| **srsENB (srsRAN)** — программная вышка на SDR | Лаборатория (этап 3–4) | Прямой доступ к измерениям из кода; естественный спутник srsRAN + Magma 1.8 |
| TR-069 / NETCONF с вендорской eNodeB | Промышленная площадка | Зависит от вендора; параметры per-UE не у всех выставлены |
| Пассивный разбор S1AP | Отладка | Хрупко, для постоянного контура не подходит |

Рекомендация: лабораторный стенд строить на **srsENB** — это снимает вопрос
«как достать измерения» полностью и совместимо с решением «оригинальная
Magma 1.8, не Charmed».

Физические константы для контракта (LTE, фиксированы стандартом):

- **Timing Advance**: шаг 16 Ts ≈ 0.5208 мкс → **≈ 78.12 м на единицу TA**;
  диапазон 0…1282. TA — это кольцо: расстояние до вышки = TA × 78.12 м ± 39 м.
- **RSRP**: диапазон −140…−44 дБм (отчёт L3: 0…97, RSRP = −140 + значение).
- **RSRQ**: −19.5…−3 дБ (отчёт 0…34).

## 3. Контракт измерений (eNodeB → ingest)

Станция пакует измерения по всем обслуживаемым UE пакетом, раз в секунду:

```json
{
  "schemaVersion": 1,
  "stationId": "enb-01",
  "ts": "2026-11-04T18:00:01.000Z",
  "ues": [
    {
      "imsi": "901700000000001",
      "ta": 3,
      "servingCellId": "cell-01",
      "rsrpServing": -78,
      "neighbors": [
        { "cellId": "cell-02", "rsrp": -92 },
        { "cellId": "cell-03", "rsrp": -101 }
      ]
    }
  ]
}
```

Правила:

- `ts` — время снятия измерения часами eNodeB; ingest при получении ставит
  серверную метку и считает смежность часов, но в окно позиционирования берёт
  серверное время.
- `imsi` связывается с тележкой через `carts[].imsi` из снимка. IMSI без
  известной тележки — отбраковка с логом, не ошибка API.
- `servingCellId` / `neighbors[].cellId` связываются со станциями через
  `stations[].cellIds`. Клетка без станции в реестре — измерение участвует
  только как «сосед неизвестен», в `stationsUsed` не попадает.
- Пакет без валидных `ues` принимается (200), просто ничего не даёт.

## 4. API ingest

```
POST /v1/measurements
Authorization: Bearer <station-token>   # токен выдаётся на станцию
```

Ответы: `202 Accepted` (принято в обработку), `400` (битый JSON, чужая
схема — с телом ошибок zod-подобного вида), `401` (токен), `409` (повтор
пакета с тем же `stationId` + `ts` в пределах окна — идемпотентный отказ).
Пакеты могут приходить с повторами: ingest дедуплицирует по (`stationId`, `ts`).

Никаких других публичных эндпоинтов в MVP: приём измерений — единственная
обязанность наружу. Всё остальное (снимок) — файловая запись для карты.

## 5. Движок позиционирования

Чистая функция, отдельный модуль (без сети и без состояния), чтобы её
можно было гонять тестами как `domain/geo.ts`:

```
window: измерения по одной тележке за последние ~2 с (скользящее окно)
     + координаты станций + профили ячеек
  → FixCandidate | null
```

Три метода по мере накопления информации, выбирается лучший доступный:

| Метод | Минимум данных | Геометрия | Ожидаемая accuracyM |
|---|---|---|---|
| `cell-id` | 1 известная ячейка | позиция станции | радиус ячейки (десятки м) |
| `ecid-ta` | serving cell + TA | кольцо TA×78.12 м ± 39 м, пересечение с полигоном ячейки | ~половина шага TA или радиус ячейки — что меньше |
| `rssi-multilateration` | 3+ ячеек с RSRP | log-distance path loss (калиброванный профиль ячейки) → оценки расстояний → наименьшие квадраты | единицы–десятки м при калибровке |

Правила качества:

- `rssi-multilateration` без калиброванного профиля ячеек **не выдаётся** —
  лучше честный `cell-id`, чем ложная точность.
- Каждый профиль ячейки (постоянная A и показатель затухания n модели
  `RSRP = A − 10n·log10 d`) калибруется на площадке измерениями на
  известных точках. Цех — металл и переотражения: заводская модель не годится.
- В `accuracyM` пишется доверительный радиус; если геометрия плохая
  (точки станций почти на одной линии, GDOP большой), кандидат понижается
  до более грубого метода.

## 6. Хронология внутри ingest

1. Принять пакет → валидация (схема раздела 3) → в скользящее окно.
2. Раз в ~1 с для каждой тележки с свежими измерениями: движок → `FixCandidate`.
3. Обновить last-known состояние: позиция, метод, `accuracyM`,
   `stationsUsed`, серверный `ts`.
4. Тележка молчит дольше порога устаревания (`STALE_AFTER_MS` = 2.5 с,
   как на карте) — из снимка убирается: плашка «нет данных» уже реализована.
5. Собрать снимок, проставить `generatedAt`, атомарно заменить файл
   (временный файл → rename), как описано в README.

## 7. Связь со ScenarioFile

Изменений схемы **не требуется**. Всё, что нужно сценарию B, уже в контракте:

- методы `rssi-multilateration` / `ecid-ta` / `cell-id` — в `PositioningMethod`;
- привязка к вышке — `Station.enodebSerial`, `Station.cellIds`;
- привязка абонента — `Cart.imsi`;
- качество — `accuracyM`, `stationsUsed` (уже рисуются кругами и цветом).

Замечание: `docs/data-contract.md` в репозитории устарел (описывает старый
`FleetSnapshot`); при взятии этапа 2/4 в работу его нужно привести к
фактическому `ScenarioFile` — это часть definition of done.

## 8. Порядок внедрения

| Шаг | Содержание | Зависимости |
|---|---|---|
| B0 | Одна srsENB + один LTE-модем + SIM: ingest принимает TA → `cell-id`/`ecid-ta`, сквозной стенд end-to-end | Машина под лабораторию, srsRAN, Magma 1.8 (Orc8r) |
| B1 | 2–3 ячейки (сектора или вторая вышка): рабочий `ecid-ta`, проверка на маршрутах с известной правдой | Координаты вышек, полевой обход |
| B2 | Калибровка path-loss по ячейкам → `rssi-multilateration` с контрольной метрикой ошибки | Измерения на эталонных точках, желательно правда-GPS для `truth` |

`truth` в `PositionFix` уже зарезервирован для контрольных прогонов — в B1–B2
тележку с GPS-логгером катать по маршруту и сверять.

## 9. Риски и открытые вопросы

1. **Часы eNodeB** — без синхронизации TA и серверное время расходятся.
   Для лаборатории: NTP на всех узлах обязателен.
2. **TA обновляется с задержкой** и не любит статику: на стоящей тележке
   кольцо «стареет». Порог свежести TA отдельный, мягче 2.5 с.
3. **RSRP-мультилатерация в цеху** — самый рискованный пункт (NLoS, металл).
   План Б — плотная сетка малых ячеек и честный `cell-id` с маленьким радиусом.
4. Кто выдаёт SIM и программирует IMSI → `carts[].imsi` (открытый вопрос 3
   из handoff-context).
5. Нужен ли MQTT для пакетов измерений или достаточно HTTP-POST —
   решить при реализации; контракт пакета от транспорта не зависит.
